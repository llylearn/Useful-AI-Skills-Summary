# 个人周报生成

## Overview

用户是工程师（前端转后端，前端后端都负责），日常会零散记录工作（可能带进度百分比、日期、重复提及同一任务）。本 skill 把这些原始记录整理成一份结构清晰的个人周报：**项目为顶层 → 项目下分前端/后端 → 端别内分【已上线】/【开发中】→ 编号排列条目**，并合并同一任务的多次提及。

核心原则：周报是"成果视图"，不是"流水账"。同一任务从 50% 推进到 100%，周报里只体现一条已完成的事项。

## When to Use

- 用户消息中出现"周报"、"个人周报"、"weekly report"等词，并且同时附带了本周的工作记录（流水、清单、聊天记录式的描述等）
- 不适用：用户只问"周报怎么写"但没有给记录（此时给通用建议即可）；用户要的是月报/季报（可借用规则但需调整时间口径）

## 标签识别（关键规则）

用户会在每条记录上附标签，指明端别和上线状态：

- **端别标签**：`【前端】` `【后端】`，也可能是 `前端`、`后端`、`前端研发`、`后端研发` 等叫法。识别关键词：含"前端"→ 前端，含"后端"→ 后端。
- **状态标签**：`【已上线】` `【开发中】`，也可能是 `已上线`、`已发布`、`上线`、`开发中`、`进行中`、`【开发】`、`开发` 等（`【开发】`/`开发` 一律按开发中处理）。
- **标签优先于内容**：用户明确标了 `【开发】`/`开发` 的记录，即使内容出现"已交付、上线、进度100%"等完成字样，也归入开发中，不改判为已上线（用户确认过的规则）。
- 状态没标时从内容推断：
  - 已上线：上线、发布、验收通过、交付、部署到生产、用户已可用……
  - 开发中：开发中、进行中、联调中、优化中、排查中、设计中……
- 端别或状态拿不准的，在周报下方注明待确认点，请用户裁决。

## 生成规则

### 1. 按项目分组（顶层）

- 先通读全部记录，识别出涉及的项目/模块名称，每个项目一个小标题。
- 同一项目下的所有工作记录放在一起，不要按时间顺序分散到多个项目里。
- 项目标题形式：`【项目名】`，与记录中用户的叫法保持一致（用户写"订单服务"就不要改成"订单系统"）。
- 无法归属到具体项目的杂项（会议、培训、环境搭建等），归入最后的"其他"分组。

### 2. 项目内分前端/后端

- 每个项目下按端别标签分成 `前端` 和 `后端` 两个小节。
- 只做了一端就只写一端，**不要为另一端留空标题**。
- "其他"分组内杂项可按标签分前端/后端（也可不分，杂项通常混在一起即可）。

### 3. 端别内分【已上线】/【开发中】

- 每个端别小节内再分 `【已上线】` 和 `【开发中】` 两个子块。
- 只出现一种状态就只写一个子块，**不要留空子块**。

### 4. 组内编号排列

- 每个子块下的工作事项用 `1. ` `2. ` `3. ` 编号，逐条排列。
- 每条一句话，动宾结构开头（完成/开发/修复/优化/联调/排查……），说清做了什么、结果如何。
- 条目的排序：重要的、完成度高的排前面。

### 5. 合并相同任务（关键规则）

- 同一任务在记录中出现多次（不同日期、不同进度），必须合并为一条。
- 典型场景：周一写"订单接口开发 50%"，周三写"订单接口开发 100%"——周报里只保留一条："完成订单接口开发"。
- **合并后保留改动页面/模块和总页面数**：同一需求的多个列表/页面合并成一条时，保留涉及的页面/模块名和总页面数（如果有），例如"基础数据需求（地下通道信息、路域信息、收费站、服务区、停车区、桥梁、隧道信息等十五个列表）"；原记录没给页面数的不编造。
- **不要把百分比搬进周报**。进度信息只用于判断任务最终状态（已完成/进行中），不体现在输出里。
- 任务尚未完成的，写当前状态即可，如"开发 XX 功能（进行中）"，同样不带百分比。
- 判断"同一任务"的依据：任务对象 + 动作一致或明显是同一事项的延续。拿不准时（例如"接口开发"和"接口联调"可能是两阶段也可能是两件事），保留为两条并在交付后向用户确认。

### 6. 时间与篇幅

- 不逐条标注日期（周报按项目组织，不按天组织）。
- 整体篇幅控制在 10-20 条事项以内；记录特别多时优先合并、次要事项可并入"其他"。

### 7. 技术细节精简

- 周报是给人（业务/领导）看的，不搬运代码层面的技术细节：接口参数名及取值（如 businessType=basic_data、deptIds）、组件/变量英文名（如 pointSelect、showAddressInput）、文件路径与文件名（如 global.less）一律省略或转成中文描述。
- 组件英文名转中文：pointSelect → 选点组件。
- 保留业务语义：如"图片上传接口参数与回显下载地址保持一致"保留，但参数的具体取值不写。

## 输出格式模板

```
周报（X月X日 - X月X日）

【项目A】
前端
【已上线】
1. 完成 XX 功能开发并上线
2. 修复 XX 页面数据不刷新问题
【开发中】
1. 联调 XX 接口

后端
【已上线】
1. 完成 XX 接口开发并发布
【开发中】
1. 开发 XX 定时任务

【项目B】
后端
【开发中】
1. 优化 XX 查询性能，耗时从 2s 降至 300ms

【其他】
1. 参加 XX 技术分享
```

- 周期从记录中的日期推断;推断不出来就省略日期行。
- 用户记录里有可量化的结果(性能数字、bug 数量等)可以保留,这是成果不是进度。

### 8. 输出到桌面 txt(用户明确要求)

- 生成周报后必须输出为 txt 文件保存到当前用户桌面。本机默认桌面为 `~/桌面`；若设置了 `DESKTOP_DIR` 环境变量则优先使用该目录。文件名带日期且不带"个人"字眼，如 `周报_20260821.txt`。
- 文件内容为纯文本(可含【】和编号),与终端输出一致,不含待确认点等元信息。

## 工作流程

1. 通读用户附带的全部记录，先摘出每条记录的标签（端别、状态）。
2. 列出涉及的项目清单。
3. 把每条原始记录分配到某个项目（或"其他"）。
4. 在每个项目内按标签分前端/后端，再按状态分【已上线】/【开发中】。
5. 在每个子块内识别同一任务的多次提及，合并成单条，丢弃百分比，确定最终状态。
6. 按模板输出：项目标题 → 端别 → 状态子块 → 编号事项。完成标准：每条原始记录在输出中有且仅有一个归宿（被合并或独立成条），无遗漏、无重复。
7. 如有拿不准的合并、端别或状态，在周报下方用一两行注明待确认点，请用户裁决。

## Common Pitfalls

1. **把百分比写进周报。** 用户明确要求不搬运百分比；"XX 完成 80%"应写作"开发 XX（进行中）"。
2. **按日期而不是按项目组织。** 流水账式周报是本 skill 要避免的核心问题。
3. **同一任务拆成多条。** "接口开发 50%"和"接口开发 100%"出现为两条 = 没有执行合并规则。
4. **擅自改项目名或任务名。** 用用户自己的叫法，便于他对照原始记录检查。
5. **遗漏不起眼的记录。** 交付前逐条核对原始记录都有归宿。
6. **把技术细节写进周报。** 参数取值、组件英文名、文件路径（global.less、deptIds、businessType 等）一律省略或转中文，见规则 7。
7. **端别标签识别错误。** 前端记录写进后端小节（或反之），标签说什么就是什么。
8. **状态推断错误。** 开发中的任务写成已上线；只有明确"上线/发布/验收通过"才算已上线。
9. **留空标题。** 没做的端别、没出现的状态，不要输出空的"后端"或"【已上线】"标题。
10. **合并时丢光页面细节。** 同一需求的多个列表/页面合并成一条时，保留改动页面/模块名和总页面数（如果有），见规则 5。

## Verification Checklist

- [ ] 每个工作事项都归属于某个项目标题下（或"其他"）
- [ ] 项目内分前端/后端，端别内分【已上线】/【开发中】
- [ ] 子块内事项用 `1. ` `2. ` 编号
- [ ] 全文无任何进度百分比
- [ ] 无同一任务的重复条目
- [ ] 每条原始记录都能追溯到输出中的某一条（无遗漏）
- [ ] 标签端别与内容一致（前端记录不在后端小节）
- [ ] 无空标题（没做的端别/状态不留块）
